03Entidades núcleo (DB)

14 tablas Postgres en Neon, orquestadas con Drizzle migrations (hasta 0007). El grafo de dependencias clavado a clients.id garantiza tenancy limpia.

clients

La barbería. 49 columnas: config Meta, Booksy, Google Calendar, Stripe Connect, fiscal, propinas, scheduling standards (minLeadTime, maxHorizon, buffer).

barbers

Staff por cliente. Hours + blockedDates por persona (null = hereda del shop), displayOrder, active. Source of truth del equipo.

bookings

Reservas. Estados: confirmed, completed, cancelled, no_show. Source: bot | booksy. `barberId` FK a barbers + `barber` snapshot string.

customers

Clientes finales por phone. Contadores noShows, cancellations, reputación (good/warning/blocked).

conversations

Estado del bot por phone. step para state machine + context jsonb (lang, followup, customerName).

invoices

Tickets (B2C) y facturas (B2B). Secuencia correlativa única por cliente. Estados: issued, voided, rectified.

payments

Cobros online (Stripe Connect destination charges). FK a invoice, idempotencia por session ID.

tips

Propinas + rating. Separada de payments. NEVER facturable (liberalidad). Incluye rating_only entries.

subscriptions

Lo que la barbería paga a otracita (29€/mes). Webhook Stripe actualiza estado.

waitlist

Clientes esperando hueco. Bot les avisa cuando se libera.

analytics

Contadores por día: mensajes recibidos, respondidos, bookings hechos, bookings cancelados.

email_parse_log

Audit de cada email Booksy entrante (status, fields missing, LLM fallback usado).

processed_stripe_events

Ledger de idempotencia para webhooks Stripe (at-least-once → effectively-once).

leads

Contactos de la landing que aún no han pagado.

04Configuración por barbería

Feature flags y ajustes que decide el dueño en el dashboard. Todos opt-in por defecto — el producto arranca con lo mínimo y se enciende a voluntad.

Info básica

Nombre, WhatsApp, dirección, email. Es lo que el bot enseña al presentarse.

Servicios

Lista de servicios (nombre, duración min, precio €). Define qué ofrece el bot.

Equipo

Cada barbero es una fila en `barbers`. Tiene nombre, orden, active flag y PUEDE tener horario + blocked propios. Si no, hereda del shop. V2: cuenta Stripe propia por barbero (modelo "alquiler de silla").

Horarios shop

Lun-Dom, hora apertura/cierre. Default para los barberos sin horario personalizado. El bot solo ofrece slots dentro (intersección barbero + shop).

Días bloqueados shop

Array de fechas ISO. Vacaciones/festivos del negocio. Los barberos pueden además añadir sus propios días blocked individuales.

Scheduling standards

3 campos en clients: `minLeadTimeMinutes` (no reservar menos de X min en advance), `maxBookingHorizonDays` (hasta cuándo), `serviceBufferMinutes` (cleanup entre citas). Defaults 15/45/5.

Datos fiscales

Nombre fiscal, NIF, dirección completa, %IVA, prefijo factura + nº siguiente. Obligatorio para activar facturación.

Facturación auto

Toggle invoicingEnabled. Valida fiscal completo antes de activarse. Emite ticket/factura por cada booking con precio.

Cobros online (Stripe)

Estado del Connect account: none | pending | active | restricted. Activable en 10 min (KYC hosted).

Propinas + rating

Toggle tipsEnabled + 3 importes sugeridos + delay minutos. Requiere Connect activo primero.

Booksy sync

URL de perfil Booksy + email sync (sync-{clientId}@inbound.otracita.es). Flag useDbAvailability.

Chatbot greeting

Mensaje de bienvenida custom del bot. Fallback a texto genérico si vacío.

Google Calendar (legacy)

Per-cliente flag useDbAvailability. Clientes antiguos siguen con GCal hasta migrar.

05Flujos completos

Cada flujo = un camino end-to-end que toca varios componentes. Verifica que ninguna pieza queda descolgada.

Flow 01 · Onboarding barbería

Desde primer click en landing hasta bot activo en producción.

  1. Barbero entra en otracita.es, clickea "Empieza ahora" → Stripe Checkout subscription
  2. Paga 29€/mes → Stripe webhook checkout.session.completed con mode=subscription
  3. Webhook: inserta row en clients (upsert por email) + row en subscriptions
  4. Notificación WhatsApp a Alex: "Nuevo cliente: X (email Y, plan Z)"
  5. Alex entra en /admin/clients, abre onboarding console del cliente
  6. Alex configura credenciales Meta (phone_number_id + token) en el editor admin
  7. Alex marca cada paso del checklist: webhook verificado, primer test, Booksy conectado
  8. Barbero recibe acceso al dashboard (Better Auth email match), configura su negocio
  9. Bot activo → primer cliente real reserva por WhatsApp
Toca: Stripe (platform) clients subscriptions notifyAlex /admin Meta WhatsApp API Better Auth

Flow 02 · Cliente reserva por WhatsApp

El happy path del producto.

  1. Cliente escribe al WhatsApp de la barbería → Meta dispara webhook
  2. Webhook verifica HMAC → engine.handleIncomingMessage()
  3. Engine resuelve el clients por phoneNumberId
  4. Intent detection (GPT-4o-mini): "quiero cortarme" → booking
  5. Bot pregunta servicio → lista interactiva desde chatbotServices
  6. Bot pregunta barbero → se cargan de barbers (active=true, ordered). Opción "sin preferencia" guarda `selectedBarberId = null`
  7. Bot pregunta fecha → próximos 7 días con huecos (respeta maxBookingHorizonDays)
  8. Bot pregunta slot → getAvailableSlotsFromDB() usa hours+blocked DEL BARBERO (o shop si null), aplica minLeadTime + serviceBuffer. Si "sin preferencia" → slot libre si al menos 1 barbero activo lo tiene libre
  9. Cliente confirma → createBooking(): si no hay barberId, pickBarberForCustomer() asigna el último barbero que atendió a ese cliente (si libre) o el menos ocupado. NUNCA persiste "Sin preferencia"
  10. Insert en bookings con `barberId` + `barber` (name snapshot), status=confirmed
  11. Si invoicingEnabled + price != null → tryAutoInvoiceInBackground() genera ticket/factura
  12. Bot confirma por WhatsApp + actualiza conversations.step = 'idle'
  13. Contador customers.totalBookings ++
Toca: Meta WhatsApp engine.ts GPT-4o-mini barbers (resolución) bookings customers conversations invoices analytics availability.ts (per-barber)

Flow 03 · Reserva desde Booksy (sync email)

Cuando el cliente reserva desde la app Booksy y queremos que el bot vea esa reserva.

  1. Cliente reserva en Booksy → Booksy envía email de confirmación
  2. El barbero tiene un forward rule de Gmail: `booksy.com → agendalo.sync@gmail.com`
  3. Gmail API + Pub/Sub notifican a /api/email/inbound (push) — coste 0€, no terceros
  4. Webhook valida firma → resuelve clients por email destino
  5. Parser regex intenta extraer: servicio, barbero, fecha, hora, duración, precio, cliente
  6. Si parse parcial → fallback a LLM (xAI Grok) para completar campos
  7. Row en email_parse_log (full/partial/failed/llm_assisted)
  8. Insert en bookings con source='booksy' + booksyBookingId (dedup)
  9. Si parse failed 3+ veces → notifyAlex() con snippet del email
  10. Auto-factura si aplica (mismo camino que flow 02)
Toca: Gmail API + Pub/Sub (pendiente activar) email_parse_log booksy-email-parser.ts xAI Grok fallback bookings invoices notifyAlex
Gap: código 100 % listo en repo (body shape Postmark heredado — se adapta el handler a Gmail Pub/Sub cuando se active). Falta crear cuenta Gmail central, activar Gmail API + Pub/Sub en Google Cloud, enseñar al barbero la forward rule. 0€/mes, no hay servicios externos contratados.

Flow 04 · Cliente cancela por WhatsApp

Limpio porque las transiciones de estado están testeadas.

  1. Cliente escribe "quiero cancelar" → intent = cancel
  2. Bot lista reservas futuras del cliente (por phone)
  3. Cliente selecciona → bot pide confirmación
  4. Confirma → bookings.status = 'cancelled' + cancelledAt
  5. tryVoidInvoicesInBackground(): si hay invoice, status = 'voided'
  6. Contador customers.cancellations ++
  7. Bot confirma cancelación
Toca: bookings invoices customers analytics

Flow 05 · No-show (barbero marca desde dashboard)

El barbero se entera en su agenda, click y listo.

  1. Barbero ve booking pasado en /dashboard/agenda
  2. Click en "Marcar no-show" → POST /api/bookings/no-show
  3. requireClientAccess valida tenant
  4. bookings.status = 'no_show'
  5. customers.noShows ++
  6. tryVoidInvoicesInBackground(): anula invoice asociada
  7. UI feedback: "Marcado no-show, factura anulada"
Toca: bookings customers invoices BookingDetailPanel.tsx
Futuro (v2): cuando un customer.noShows ≥ N configurable por barbero, al reservar siguiente vez el bot pide depósito por anticipado (solo para ese cliente). Integración con flow de propinas/cobros.

Flow 06 · Recordatorio día anterior (cron 10am)

Cron diario que envía recordatorio + botón confirmar/cancelar.

  1. Vercel Cron dispara GET /api/cron/reminders a las 10:00 Europe/Madrid
  2. requireCron() valida Authorization: Bearer $CRON_SECRET (timingSafeEqual)
  3. Query: bookings con date=tomorrow, status=confirmed, reminderSent=false
  4. Para cada → WhatsApp con 2 botones: "Confirmo" / "Cancelar"
  5. Marca reminderSent = true (idempotente si cron corre 2x)
  6. Si cliente tap Cancelar → engine dispara flow de cancelación
Toca: Vercel Cron bookings conversations (lang) Meta WhatsApp

Flow 07 · Cobro online (QR en agenda)

Barbero genera QR desde el detalle de la reserva, cliente escanea y paga.

  1. Barbero abre booking en /dashboard/agenda/[bookingId]
  2. Panel "Cobrar online" → ajusta importe → click "Generar QR"
  3. POST /api/payments/create-link → crea checkout.session destination charge → row en payments (pending)
  4. UI muestra QR (librería qrcode) + URL copiable
  5. Cliente escanea con móvil → hosted Stripe Checkout
  6. Paga con tarjeta/Apple Pay → Stripe webhook checkout.session.completed
  7. Webhook: payments.status = 'succeeded' + paidAt + IDs
  8. Si invoice asociada: invoices.paidOnlineAt = now (sin tocar fiscal status)
  9. Notificación WhatsApp a Alex con importe + cliente
  10. UI del panel detecta con poll cada 4s → muestra "Pagado ✅"
Toca: BookingDetailPanel.tsx Stripe Connect (destination charge) payments invoices (paidOnlineAt stamp) processed_stripe_events (idempotencia) notifyAlex
Bloqueante actual: el platform profile de Stripe Connect aún no ha sido signed up en live. Al hacer click en "Activar cobros online" devuelve error. Fix: Alex completa el formulario en dashboard.stripe.com/connect (modelo: Platform/SaaS).

Flow 08 · Rating + propina post-servicio

Shipeado + migración aplicada (2026-04-22). Deploy live en otracita.es. Pendiente: flipear FOLLOWUP_DRY_RUN=false en Vercel env y validar con tu barbería de prueba. Por plan Hobby corre diario a 21:00 en vez de cada 10 min.

  1. Cron /api/cron/post-booking-followup cada 10 min identifica bookings con endsAt+30min ≤ now, tipsEnabled=true, followupSentAt=null
  2. sendRatingMessage(): WhatsApp lista con 5 ⭐ + marca followupSentAt + guarda context.followup
  3. Cliente tap ⭐⭐⭐⭐⭐ → engine intercepta fu_rate_5 → handleFollowupReply()
  4. Insert tips row (status='rating_only', amount=0, rating=5)
  5. Rating ≤ 3 → "Gracias, se lo pasamos al equipo" + clear state. Fin.
  6. Rating ≥ 4 → WhatsApp 3 botones: "2€" / "3€" / "No, gracias"
  7. Cliente tap "3€" → createTipSession() → Stripe Checkout URL + row tips pending + rating carried over
  8. Cliente paga → webhook rama otracita_tip=true → tips.status = 'paid' + paidAt
  9. Rating visible en dashboard (v2). Propina en export XLSX sheet "Propinas".
Toca: Cron (Vercel) tips bookings (followupSentAt) conversations.context.followup engine.ts (hook early) followup.ts Stripe Connect (destination) XLSX export (sheet Propinas)
Estado: live en producción. Stripe Connect platform signup ✅. Bloqueante único: FOLLOWUP_DRY_RUN=false env en Vercel cuando valides en tu barbería de prueba.

Flow 09 · Facturación automática (RD 1619/2012)

El anti-Booksy: el barbero recibe el libro mensual listo para el gestor sin mover un dedo.

  1. Booking se crea (flow 02 o 03) con price != null y cliente con invoicingEnabled=true
  2. tryAutoInvoiceInBackground(): decide ticket (sin NIF) o factura (con NIF)
  3. Genera número siguiente con invoiceNumberPrefix + invoiceNumberNext
  4. Insert atómico en invoices + incrementa secuencia (locking)
  5. Snapshot de datos cliente + servicio al issue time (inmutable)
  6. Calcula base imponible + cuota IVA + total en cents
  7. Fin de mes, barbero va a /dashboard/facturas
  8. Descarga: Libro PDF (A4, legal) + CSV Excel-ES + XLSX (Resumen + Facturas + Propinas)
  9. Adjunta al email de su gestor → Modelo 303
Toca: invoices bookings clients.fiscal* React-PDF (Libro) ExcelJS (XLSX) Excel-ES CSV helper

Flow 10 · Barbería cancela su suscripción a otracita

"Cancelas en 1 click, sin permanencia" — tiene que ser real.

  1. Barbero entra /dashboard/negocio → busca "Gestionar suscripción"
  2. POST /api/stripe/portal → crea Billing Portal session
  3. Redirect a hosted Stripe Portal → cancela suscripción
  4. Stripe webhook customer.subscription.deleted
  5. Webhook: subscriptions.status = 'cancelled' + cancelledAt
  6. También clients.status = 'cancelled' → el bot deja de responder para ese tenant
Toca: Stripe Billing Portal subscriptions clients.status

07Matriz de estado: Booking × Everything

Para cada transición de estado de una reserva, qué hace cada subsistema. Esto se actualiza siempre que se añada un estado nuevo.

bookings.status Factura Cobro online Rating + propina Recordatorio Contador cliente
confirmed (futuro) Auto-emitir ticket/factura si invoicingEnabled + price Disponible (QR desde agenda) Aún no (endsAt no pasó) Si date=mañana → cron envía totalBookings ++
confirmed (pasado, endsAt+30min) Sigue issued Disponible Cron envía si tipsEnabled + followupSentAt null — —
completed Sigue issued Disponible Sí (mismo criterio) — —
cancelled Void asociada Session expira → cancelled Nunca enviar No enviar cancellations ++
no_show Void asociada Session expira → cancelled Nunca enviar No enviar noShows ++
undo no_show → confirmed Restaura issued (MVP — estrictamente rectificativa) Disponible de nuevo Reanclar a nuevo endsAt — noShows —
Regla durabilidad: cada vez que se añada un nuevo estado o transición, actualizar esta tabla + la API que ejecuta la transición + los tests de invariantes. El anti-patrón "dos features en paralelo, interacción no testeada" fue cómo se escapó el no_show → void invoice en la primera iteración.

08Capas transversales

Temas que atraviesan todo el producto — seguridad, compliance, observabilidad.

🔐 Multi-tenancy

requireClientAccess() en TODA API de tenant. Resuelve cliente por session de Better Auth, bloquea cross-tenant.

  • Webhooks (WhatsApp, Stripe, email) bypass con su propia firma
  • Admin tiene su propio requireAdmin

🔏 Verificación HMAC

Meta webhook firma X-Hub-Signature-256, Stripe firma Stripe-Signature.

  • Comparación timingSafeEqual (no ===)
  • Cron secret por header Authorization: Bearer

🔁 Idempotencia

Stripe retry at-least-once → tabla processed_stripe_events con PRIMARY KEY event_id. ON CONFLICT DO NOTHING.

  • Belt-and-braces: UPSERT en las filas tenant también
  • Cron followup: followupSentAt marca como enviado

📊 Observabilidad

Logs estructurados con prefijos [stripe-webhook], [cron/...], [notifyAlex].

  • Tabla email_parse_log para Booksy
  • analytics por día (mensajes, bookings)
  • Alertas a WhatsApp de Alex en eventos críticos

⚖️ Compliance fiscal ES

Real Decreto 1619/2012.

  • Ticket < 400€ sin NIF, factura completa con NIF
  • Secuencia correlativa única por cliente (locking)
  • Snapshot inmutable de datos al emitir
  • Propinas fuera del libro de facturas (liberalidad, no contraprestación)
  • TICKET_MAX_CENTS = 40000 guard

🛡️ GDPR / LOPD-GDD / LSSI-CE

Páginas /privacidad, /terminos, /aviso-legal.

  • Customer data: phone + name + bookings. Derecho de supresión en v2
  • No sell data, no tracking third-party

💾 Backups / DR

Neon branches = snapshot automático. Pero no hay test formal de restore.

  • Migraciones versionadas en drizzle/
  • Purely additive migrations by default (no drops)

🌍 i18n

Bot bilingüe ES/EN con auto-detect. Dashboard solo ES (target ES-only por ahora).

🎨 Brand

Light theme único. Terracotta #C9653C, cream #F7F3EE, espresso #2A1D14, Fraunces+Inter.
